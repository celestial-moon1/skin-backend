Skin backend for a certain blocky game. (Code generated by Haiku 5.5 & Deepseek V4.1 Flash)

## Arm model (classic / slim)

Each skin has an arm model, chosen on the upload page:

- **classic** — 4-pixel arms (the default)
- **slim** — 3-pixel arms (Alex)

The PNG size cannot carry this choice: a slim and a classic skin are usually both 64x64, so the
model is stored in its own `skins.model` column and sent back to the game.

Endpoints:

- `PUT /me/skin?model=classic|slim` — stores the PNG and the model. A missing or unknown value
  falls back to `classic`, and the response echoes the stored value.
- `GET /skins/<xuid>` — returns the PNG and the model in the `X-Skin-Model` header. A client that
  sees no header should assume `classic`.
- `GET /upload` — pre-selects the model already stored, so re-uploading keeps the player's choice.

## Capes

A cape is stored in its own `capes` table, keyed by the same XUID, so a player can wear a custom skin and a
custom cape at the same time. A cape has **no arm model**: the classic/slim choice applies to skins only.

Endpoints:

- `PUT /me/cape` — stores the cape PNG for the logged-in account. No query parameters.
- `GET /capes/<xuid>` — returns the cape PNG, or 404 when the player has none. No `X-Skin-Model` header is
  sent: the game renders a cape from the model's own UVs and ignores the header for capes.
- `GET /upload` — the page shows the current cape next to the current skin and uploads each separately.

The game draws the cape from the 10x16 area at the top left of the sheet, so a classic 64x32 cape sheet is
stored and served as drawn. Both sizes accepted for skins (64x32 and 64x64) are accepted for capes.

## Health and deploys

`GET /health` returns `{ "ok": true, "commit": "<sha>" }`. The commit is the revision the running
process was built from, read from Render's `RENDER_GIT_COMMIT`; off Render it is `null`. Check it
after a push to confirm the new code is actually live rather than still building:

```
curl -s https://skin-backend-o3bg.onrender.com/health
```

The database schema is applied on every boot (`server.js` runs `schema.sql` at startup), so an added
column arrives with the deploy and needs no manual migration.
